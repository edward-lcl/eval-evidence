## 1. Verdict

Starting from what a reader sees — rank 1 on `https://www.tbench.ai/leaderboard/terminal-bench/2.0`, "NexAU-AHE / GPT-5.5 / 84.7% ± 2.1 / 2026-05-14", no verified badge — I could reconstruct **more than I expected but by inference rather than by disclosure**. The population (89 tasks × 5 attempts = 445 trials, from four separately-run Harbor jobs uploaded as one HuggingFace PR), the task revision (all 89 tasks pinned to `laude-institute/terminal-bench-2@69671fba…`, and every one of the 142 rows shares the same per-task content checksums), and the trial-level rewards are all publicly downloadable for this row. However, the two decisions that turn 445 rewards into "84.7% ± 2.1" — (a) which errored trials are dropped from the denominator and (b) the aggregation and standard-error formulas — are **not documented anywhere for the 2.0 leaderboard**; I recovered them only by numerically matching candidate rules against three rows (NexAU-AHE, Terminus 2 + GLM-5, Gemini CLI + Gemini 3.1 Pro) and against the successor (2.1) leaderboard's now-public code. The result differs from Harbor's own job-level `mean` (376/445 = 84.49%, which is also the number the submitter put in their PR title) by +0.22 pp because two infrastructure-failed trials were silently removed from the denominator; the "±" means 1.96 × a within-task-only SE on the 2.0 page but 1 × SE on the 2.1 page of the same site. Harness version, image digests, and the exact exclusion predicate are UNAVAILABLE for this row; the row's own review record (the HF PR) is no longer publicly readable (discussions disabled). The vendor half of the lane shows a second layer of non-comparability: OpenAI's "82.7%" for GPT-5.5 does not match the leaderboard's verified Codex CLI row (82.2% ± 2.2), Anthropic's Opus 4.7 "69.4%" was run with a resource allocation ("1× guaranteed / 3× ceiling") that the leaderboard rules forbid, and both vendors republish each other's numbers without harness disclosure. **The abstraction that is missing is not per-trial evidence (that exists) but a versioned, machine-readable "claim manifest" that names the trial population, the exclusion predicate, and the aggregation/uncertainty rule; the 2.1 process partly supplies exactly that (submission JSON with `source_jobs`, `source_filter`, `disqualified_trials`, `trials[]`, `metrics`, plus public metric code) and is the strongest evidence in this lane that the abstraction is both necessary and cheap.**

### 2.9 Aggregation rule and where the code is

- **DERIVED (exact on 3/3 rows tested; consistent with 142/142 detail pages)** — 2.0 accuracy = (1/89) Σ_i (successes_i / counted_trials_i). This is a *mean of per-task means*, which equals the pooled trial mean only when every task counts the same number of trials. For every one of the 142 rows the sum of `avgResolutionRate` over the detail page's tasks divided by 89 reproduces the row's `accuracy` to machine precision.
- **UNAVAILABLE** — The 2.0 importer code (see 2.2). The successor's code is public: `harbor-framework/terminal-bench-2-1@7131e4375048a0e408a8fb404b5f499d726b695b:leaderboard/src/leaderboard/core/metrics.py` — `compute_metrics`: "accuracy = successful / total trials, matching the Harbor importer"; `is_success(reward) = reward > 0`; errored trials have no reward → failure; disqualified trials are joined in as reward 0. **CONFLICTING** — the 2.1 comment says "matching the Harbor importer" (pooled successful/total), but the 2.0 page numbers are per-task means with dropped trials (e.g. NexAU pooled = 376/443 = 84.88%, per-task-mean = 84.72%, displayed = 84.72%). Either the 2.0 importer differs from what the 2.1 author calls "the Harbor importer", or the two coincide only in the no-dropped-trials case. Both readings preserved.
- **OBSERVED** — SUBMIT.md (2.1): "Errored trials count as `reward 0` — they are not excluded from the metric." and the bot's static-analysis footer: "Errored trials count `reward 0` in the metric computation." — an explicit, public rule that the 2.0 page did not have.

### 2.10 Uncertainty

- **DERIVED (exact on NexAU-AHE, GLM-5, both Gemini CLI rows)** — 2.0 `stderr` = (1/T)·sqrt(Σ_i s_i²/n_i) with T = 89, s_i² the sample variance (ddof = 1) of the counted trial rewards of task i and n_i its counted trials; equivalently (1/T)·sqrt(Σ_i p_i(1−p_i)/(n_i−1)). For NexAU: 0.010659362899443978 vs site 0.010659362899443975. This is a *fixed-tasks* SE: it propagates only within-task Bernoulli noise and ignores between-task variance (the SE of the 89 per-task means would be ≈ 0.032, three times larger); the naive binomial SE over 445 trials would be 0.017.

## 5. Implications for the central question

1. **Verifying a trial is easy here; reconstructing the row is not, and the gap is exactly the "denominator + rule" layer.** For row 1 every trial's reward, verifier output and (ATIF) trajectory are downloadable, and task identity is pinned twice (git commit + dirhash). What is not written down anywhere the reader can reach: which trials count, how they are aggregated, and what "±" means. I recovered these only because (a) numbers are exact rationals with denominators of 89·k that betray the rule, (b) three rows with different error mixes were available to discriminate candidates, and (c) the successor project published its metric code. A reader without those three accidents cannot get from 445 rewards to "84.7% ± 2.1", and would compute 84.49% (Harbor's own metric, and the submitter's own claim) or 84.88% (pooled over counted trials).

2. **The differences are small on the top row and large elsewhere — which is why they need to be declared, not discovered.** +0.22 pp for NexAU; a 2-row split with 2–3 trials/task for Gemini CLI; rows with 1 trial/task shown alongside 5-trial rows; 8 rows with "± N/A" for a reason nobody states; a within-task-only SE that is ~3× smaller than a between-task SE. Any of these could flip adjacent ranks (rows 4 and 5 are 82.2% ± 2.2 vs 82.2% ± 2.8).

3. **"Verified" is a provenance claim about who ran it, not an evidence claim.** The top verified row (Codex CLI GPT-5.5) exposes fewer artifacts (no trajectory, no tokens, no config, no harbor version) than the unverified community row above it. A badge that means "we ran it" without an attached bundle is a trust transfer, not a reconstruction path.

4. **Vendor numbers are a different population again and are cross-published without disclosure.** OpenAI 82.7 vs leaderboard 82.2; Anthropic Opus 4.6 65.4 (Terminus-2, thinking off, 3× resource ceiling — a configuration the leaderboard forbids) vs leaderboard 62.9; identical third-party numbers (69.4/68.5) on both vendor pages. What is missing is not trials but a statement of harness, attempts, exclusion and aggregation — the same manifest.

5. **The maintainers' own next iteration is evidence that the abstraction is necessary and cheap.** TB 2.1 replaced "PR a folder of Harbor jobs" with a per-row JSON that names `source_jobs`, a `source_filter` (agent, version, model, effort), `disqualified_trials` with reasons and judge links, the full `trials[]` id list, and `metrics` computed by public code with an explicit errored-trials rule and an explicit SE formula, plus leaderboard-owned trial clones "so the record can't be mutated or deleted later" and a git history per row. That is roughly the "claim manifest" the eval-evidence `UPSTREAM_MAP.md` gestures at ("Published-claim membership … Aggregation lineage … leaderboard/publication layer"). It also shows the residual gaps even with the manifest: the disposition of judge flags is a comment-thread decision with no recorded rationale; costs were backfilled after merge and now disagree between the row and the Hub; "±" silently changed meaning between 2.0 and 2.1; the dataset iterated to version 6 while sharing the name "Terminal-Bench 2.1".

6. **Is a new abstraction unnecessary?** For *trial* evidence: yes, largely — Harbor's `result.json` + ATIF + verifier artifacts + `task_checksum` + (since 2026-04-29) `lock.json` already cover it, and the eval-evidence per-trial bundle would add little to what the HF folder already carries. For *claim* evidence: no — nothing in Harbor's per-trial or per-job outputs records which trials a published number used, why others were dropped, or how the number and its interval were computed; the 2.0 leaderboard demonstrates that this layer was implemented as private importer behaviour, and the 2.1 leaderboard demonstrates that making it a small, versioned, machine-readable file plus ~250 lines of public metric code is sufficient to make the row reconstructable to the last decimal (I reproduced 83.82/1.16 from its own definitions in principle; the 2.0 numbers I could only reverse-engineer). Retrospectively recoverable for 2.0: population, task revision, per-trial rewards, and (by inference) the rules — for HF-submitted rows only. Prospectively capturable: harbor version, agent revision, image digests, exclusion predicate, aggregation/SE code hash, and the manual dispositions (judge overrides, backfills) as first-class entries. Fundamentally external: vendor-side runs (OpenAI 82.7, Anthropic 69.4/65.4) whose harness and population live in private infrastructure and are disclosed, at best, in a footnote.
