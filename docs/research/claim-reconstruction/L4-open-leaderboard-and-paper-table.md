## 1. Verdict (one paragraph)

Both cases are far richer than a typical leaderboard row or paper cell, and in both the *per-trial* evidence is largely intact and public (lm-eval results JSON with task/prompt/target content hashes, model revision, harness short hash, seeds, dtype, batch size, env info; SWE-bench per-instance eval logs, patches and agent trajectories on a public S3 bucket). Despite that, the reported number could be reproduced only up to a set of *un-recorded transitions* that sit above the trial: (C) the same model row was fed by four successive `results_*.json` files — two genuine runs against two different model revisions under two harness commits, plus two in-place batch re-scorings (Oct 2024, Feb 2025) that rewrote `results.*.exact_match` while leaving `groups.*`, the top-level `leaderboard` aggregate, `stderr`, and `configs.*.metadata.version` stale; the displayed `Model sha` is the sha of the *first* run while every displayed score comes from the *last* rewrite of the *second* run (confirmed on 4 further models); the harness commit `9694c56` for the run that produced the displayed scores resolves to no public commit; the results→contents aggregator script is not public; the per-sample files that would prove "same generations, only re-scored" are gated. (D) 286/2294 = 12.47% and 87/2294 = 3.79% reproduce exactly from `results.json`, but the released prediction file for the headline run has 2,283 lines covering 2,266 distinct instances (12 instance ids duplicated, 9 with different patches; 28 test instances have no prediction line; 154 empty patches), the harness that adjudicated duplicates is unrecorded (pre-Docker conda harness, no version in logs), the repo README carried 12.29% from 2024-04-05 to 2024-05-28 while the paper said 12.47% from v1 on, with no retained explanation of the +4 instances; the "3.8% [20]" baseline is not in the cited paper (which says 1.96%) but in a later leaderboard run of the same team; and SWE-Bench+ (arXiv 2410.06992) later re-read the identical resolved set and reported 12.47% → 3.97% after excluding solution-leak and weak-test instances — measurements unchanged, interpretation changed. Mechanical derivation ends exactly where the record stops describing *which* artifact version, *which* key, and *which* population an aggregate was computed over; a byte-sealed per-trial envelope would not have closed any of the gaps found here, whereas a small, dated, campaign-level ledger of "row fed by file X, key Y, transform Z, population P" would have closed most of them.

## 5. Implications for the central question

**Where mechanical derivation ends.** In both cases the arithmetic from retained per-task/per-instance numbers to the displayed number is fully mechanical *once three choices are supplied that the record does not state*: (i) which artifact version feeds the display (HF: file 4 of 4, not the file whose sha is displayed; SWE: `results.json` in a history-reset repo whose earlier state is gone), (ii) which key inside the artifact (HF: `results.<task>` not `groups`/`leaderboard`/stderr; SWE: the `resolved` list, not the trajectory/log inventory whose counts disagree with each other), and (iii) which population (HF: latest rewrite of the second run; SWE: 2,294 including 28 absent, 154 empty, 12 duplicated). Everything below those choices was OBSERVED and re-derivable to full precision (C6, D2). Everything above them is ASSERTED by maintainers (blog, discussion, README) or simply UNAVAILABLE.

**Which transitions had no retained record.** (a) Model-row replacement by a re-run under a new revision (HF C2/C4/C5) — the request file is overwritten, the display keeps the old sha; (b) in-place metric re-application over stored generations (HF C3/C10/C11) — one undescribed upload commit, dependent fields left stale, per-sample proof gated; (c) prediction dedup and denominator (SWE D3); (d) count change 282→286 (SWE D5); (e) evaluation-harness identity (HF short hash unresolvable; SWE none) ; (f) artifact custody moves (SWE git→S3→renamed bucket) without a digest chain. Note that (a)–(d) are all *campaign/claim-level* events, not per-trial events.

**On the eval-evidence hypotheses (RESEARCH_MAP.md).**
- H1 (explicit provenance states prevent misleading interpretation): supported in a specific form. The misleading elements here are *not* missing fields — the HF file is unusually complete — but silently *mixed-provenance* fields (sha from run 1, scores from run 2 rewrite 2; `results` rescored, `groups`/stderr not). A per-value "which input, which transform, when" pointer (the structured-provenance prototype) is exactly what would have exposed C3/C4; a top-level "available_fraction" would have scored this file ~100% and been wrong about it.
- H3 (post-run byte sealing adds value): weakly supported and only in a specific place. Sealing the per-trial file would not have flagged anything in C or D — the maintainers *intended* to rewrite. What was missing is a sealed record of the *aggregate's inputs* (which file, which key) and, for SWE, a digest of `all_preds.jsonl` at evaluation time. Content-addressed storage already exists in both ecosystems (HF git, S3 ETags) but is not *referenced* by the claim.
- H4 (trial evidence is a useful unit): the falsifying observation is present. Denominator, selection, retry and aggregation ambiguity dominated both cases even though per-trial records were near-complete; the useful missing unit is a small dated ledger at the row/cell level.
- H6 (retrospective reconstruction is economical): mixed. Retrospective reconstruction here cost several hours per case and still left the six UNAVAILABLE items above; three of them (harness commit, dedup rule, count change) would have been free to capture prospectively.

**Is the proposed abstraction unnecessary?** For the per-trial layer, largely yes for these two ecosystems: lm-eval's results JSON and HELM's per-run directory already carry model revision, seeds, dtype, env, prompt/doc/target content hashes, per-instance stats and predictions; SWE-bench's submissions carry per-instance logs, patches and trajectories. A generic per-trial envelope would mostly re-encode what is already there and would still not resolve `9694c56`. What is *not* provided by any of the three sources and is where every un-recorded transition sat is a claim-level record with roughly: `displayed value ← {input artifact + digest + key path} × {transform + version} × {population/denominator + inclusion reasons} × {date, actor, reason}` and a per-value provenance state so that a mixed-provenance row (C4) is visibly mixed. The lane's evidence therefore favours shrinking the trial envelope to an interchange record and spending the effort on the row/cell ledger and its "unmatched conditions" list, which is what the claim-specific decision prototype in RESEARCH_MAP.md already sketches. Digest ≠ correctness applies throughout: HF's `task_hashes` proved the inputs *changed* between two runs and could not say *what* changed (C8); an exact float reproduction of 47.98… (C6) certifies the arithmetic, not that the underlying generations, the harness, or the rescoring were right.
