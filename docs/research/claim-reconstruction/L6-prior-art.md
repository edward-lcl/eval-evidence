## 1. Verdict (one paragraph)

Nothing mature already implements "claim lineage" for AI-evaluation results — i.e., a machine-checkable chain *retained trials → eligible → included cohort → transformations → aggregation → reported number → table location → claim* with an explicit "we do not know" state per field. But almost every *piece* exists somewhere, and several are closer than the eval-evidence docs assume. (i) W3C PROV-DM already has the exact relational vocabulary (Entity/Activity/Agent, `wasDerivedFrom`, `wasRevisionOf`, `wasInvalidatedBy`, `alternateOf`, `Collection`/`hadMember`, `Bundle` = provenance of provenance) and, via PROV-CONSTRAINTS, an explicit statement that validity ≠ truth; what PROV cannot express is *unavailability* (open world: absence is not "unknown"). (ii) Inspect AI's log format is the strongest in-domain precedent: it already records per-sample `invalidation: ProvenanceData{author, reason, timestamp}`, post-hoc `log_updates` with provenance, `error_retries`, `total_samples` vs `completed_samples`, `scored_samples`/`unscored_samples`, `EvalRevision{origin, commit, dirty}`, and `packages` — a real "selection/denominator history" primitive that eval-evidence's own STATE_REGISTER lists as a Known gap. (iii) MLPerf is the only mature *governance* system in which "a leaderboard row is supported by these evaluations" is enforced (fixed directory-per-result layout, LoadGen-produced logs, a submission checker that verifies seeds/min-duration/min-query-count/compliance tests, peer objections, audits, and the rule "Results that cannot be replicated are not valid results") — but it is a procedure plus a directory convention, not a portable evidence data model, and it does not model unavailability either. (iv) in-toto attestations are a natural *binding/signing* layer for a per-transition predicate chain (Statement = subject digests + predicateType + arbitrary predicate; the Test Result and SCAI predicates already carry `passedTests/failedTests` and `attribute+conditions+evidence`), but in-toto supplies no evaluation semantics — the predicate schema is exactly the thing that would still have to be written. (v) The claim-support layer (evidence + controls + assumptions + unresolved alternatives ⇒ interpretation) exists only in scientific-communication models: nanopublications (assertion/provenance/pubinfo split, content-hash Trusty URIs, `npx:retracts/supersedes/invalidates`), Micropublications (claim + `supports`/`challenges` + "transitively close claim lineages to underlying empirical evidence"), and GRADE (per-outcome certainty with named down/up-rating domains). Frank recommendation: do not invent a new provenance model. Profile PROV-DM (or its RO-Crate/schema.org serialization) for the lineage graph, borrow Inspect's invalidation/log-update pattern for exclusion history, add an explicit unavailability marker (precedent: SLSA v0.2 `metadata.completeness.*` booleans and EEE's `"unknown"` convention), and use in-toto Statements only if signing/binding is wanted. The genuinely missing thing — a claim-specific "required evidence → state → unresolved differences → decision" record — has no established equivalent and is the only part worth building; the trial-level byte-sealing bundle is the most redundant part.

## 2. Findings with labels and receipts

### 2.1 W3C PROV (PROV-DM, PROV-O, PROV-CONSTRAINTS)

- **OBSERVED** — PROV-DM is a W3C Recommendation dated 30 April 2013 (https://www.w3.org/TR/2013/REC-prov-dm-20130430/). Definitions (section numbers from the spec):
  - Entity §5.1.1: "a physical, digital, conceptual, or other kind of thing with some fixed aspects; entities may be real or imaginary."
  - Activity §5.1.2: "something that occurs over a period of time and acts upon or with entities …"
  - Agent §5.3.1: "something that bears some form of responsibility for an activity taking place, for the existence of an entity, or for another agent's activity."
  - Derivation §5.2.1 (`wasDerivedFrom`): "a transformation of an entity into another, an update of an entity resulting in a new one, or the construction of a new entity based on a pre-existing entity."
  - Revision §5.2.2 (`wasRevisionOf`): "a derivation for which the resulting entity is a revised version of some original."
  - Quotation §5.2.3, Primary Source §5.2.4 (`hadPrimarySource`).
  - Invalidation §5.1.8 (`wasInvalidatedBy`): "the start of the destruction, cessation, or expiry of an existing entity by an activity. The entity is no longer available for use after invalidation."
  - Specialization §5.5.1, Alternate §5.5.2 ("Two alternate entities have the same general entity they both refer to").
  - Collection §5.6.1 / `hadMember` §5.6.2 / `prov:EmptyCollection`.
  - Bundle §2.2.2: "a named set of provenance descriptions, and is itself an entity, so allowing provenance of provenance to be expressed."
  - §2.1.2: "PROV does not attempt to specify the conditions under which derivations exist; rather, derivation is considered to have been determined by unspecified means."
- **OBSERVED** — PROV-O (W3C Recommendation 30 April 2013, https://www.w3.org/TR/prov-o/) mirrors these as `prov:Entity/Activity/Agent`, `prov:wasDerivedFrom`, `prov:wasRevisionOf`, `prov:wasInvalidatedBy`, `prov:hadPrimarySource`, `prov:hadMember`, `prov:Bundle`, `prov:Plan`, `prov:SoftwareAgent`, plus qualified forms (`prov:qualifiedDerivation` → `prov:Derivation` with `prov:hadUsage`, `prov:hadGeneration`, `prov:hadActivity`; `prov:hadRole`; `prov:value` "provides a literal value that is a direct representation of an entity").
- **OBSERVED** — PROV-CONSTRAINTS (https://www.w3.org/TR/prov-constraints/) §1.2: "A valid PROV instance corresponds to a consistent history of objects and interactions to which logical reasoning can be safely applied," and: "our notion of validity of a PROV instance/document is closer to logical 'consistency'." Also "PROV instances need not be valid."
- **DERIVED** — Consequence for the lane question: PROV distinguishes *description* from *truth* explicitly (validity = consistency), and can express supersession (`wasRevisionOf`), removal from use (`wasInvalidatedBy`), same-thing-different-view (`alternateOf`/`specializationOf`), membership (`Collection`/`hadMember`), and provenance-of-provenance (`Bundle`). It has **no** construct for "value unknown/unavailable": under PROV's open-world semantics an absent statement is simply not stated. There is likewise no standard vocabulary for "excluded and why" — a profile would have to encode exclusion as an Activity with a `prov:Plan` and a role, or as `wasInvalidatedBy` + annotation.
- **UNAVAILABLE** — I did not verify whether PROV-Dictionary / PROV-Links (`mentionOf`) add anything decisive; not fetched.

### 2.2 ProvONE (scientific-workflow provenance)

- **ASSERTED/OBSERVED (partial)** — ProvONE HTML at https://github.com/DataONEorg/sem-prov-ontologies/blob/master/provenance/ProvONE/v1/provone.html (title "ProvONE: A PROV Extension Data Model for Scientific Workflow Provenance", Draft 01, May 2016; the purl https://purl.dataone.org/provone-v1-dev redirected to a Jenkins host that returned HTTP 503 at fetch time). Splits *prospective* provenance ("captures the procedure or 'recipe' required to produce a data artifact … the workflow specification") from *retrospective* provenance (execution traces); classes Program/Port/Channel/Execution/Data/Workflow/Controller/User; properties `hasSubProgram`, `hasInPort`, `hasOutPort`, `wasPartOf`, `hadInPort`, `hadEntity`, `hasDefaultParam`; subclasses PROV.
- **DERIVED** — The prospective/retrospective split maps well onto eval-evidence's "expected attempts (locked config)" vs "discovered/retained trials"; ProvONE gives vocabulary but no notion of exclusion reason or unavailability.
- **NOT FETCHED** — Kepler, Taverna, noWorkflow, YesWorkflow: from general knowledge these are capture/annotation tools built on the same prospective/retrospective idea (noWorkflow captures Python "trials"; YesWorkflow annotates scripts); not opened in this lane.

### 2.3 Research Objects / RO-Crate / Workflow Run RO-Crate

- **OBSERVED** — Process Run Crate profile 0.5 (`https://w3id.org/ro/wfrun/process/0.5`, https://www.researchobject.org/workflow-run-crate/profiles/process_run_crate/): an execution is a schema.org `CreateAction` with `instrument` (MUST), `object` (inputs, MAY), `result` (SHOULD), `startTime`/`endTime`, `agent`, `actionStatus` (`CompletedActionStatus`/`FailedActionStatus`; "If unspecified, consumers should assume successful completion"), `error`, `environment` → `PropertyValue`. Multi-file results use `Collection` with `hasPart`/`mainEntity`.
- **OBSERVED** — Provenance Run Crate 0.5 (`https://w3id.org/ro/wfrun/provenance/0.5`): steps are `HowToStep` + `ControlAction`; parameters link via `FormalParameter`/`exampleOfWork`; `ParameterConnection`. On failure: `ControlAction`/`OrganizeAction` "SHOULD be `FailedActionStatus` if [the step] failed to complete". On skipping: "If an execution of a step is skipped … the corresponding action SHOULD NOT be included in the RO-Crate metadata." Cancelled/retried: no provisions. Unknown values: no guidance.
- **DERIVED** — This is a decisive negative for the lane question: the leading workflow-provenance packaging profile *removes* skipped executions from the record rather than recording them with a reason. It represents absence, not "unavailable" or "excluded because …". It also defaults an unspecified status to success (convenient default of exactly the kind eval-evidence's DECISION_GATE calls a defect).
- **UNAVAILABLE** — Profile release dates were not on the fetched pages.

### 2.4 CWLProv, ReproZip (reproducibility infra)

- **OBSERVED** — CWLProv 0.6.0 (`https://w3id.org/cwl/prov/0.6.0`; https://github.com/common-workflow-language/cwlprov, prov.md): workflow runs `prov:type='wfprov:WorkflowRun'`, steps `wfprov:ProcessRun`; data identified by `urn:hash:sha1:` URIs; collections via `prov:Dictionary`/`prov:hadDictionaryMember` or `ro:Folder`; `prov:used`/`wasGeneratedBy`; nested workflow provenance in separate files linked by `prov:has_provenance`; timestamps/agents via `wasStartedBy(...)`. **No coverage** of failed/skipped/retried steps; no reproducibility "levels" text found.
- **OBSERVED** — ReproZip 1.x (https://docs.reprozip.org/en/1.x/packing.html): `reprozip trace` uses `ptrace` to capture "all the system calls issued, storing them in an SQLite database"; `config.yml` sections `runs`, `inputs_outputs`, `packages`, `other_files`, `additional_patterns`; multiple runs supported ("the final bundle will be able to reproduce any of the runs"). Does not state what it does not capture.
- **DERIVED** — Both are execution-capture, not claim reconstruction. Unit = one execution / one workflow run. Neither models selection or aggregation of many runs.
- **NOT FETCHED** — Sciunit, Snakemake report, Nextflow HTML report details (Nextflow trace record: see 2.7).

### 2.5 Nanopublications, Micropublications, SEPIO, GRADE, DISK (claim / evidence models)

- **OBSERVED** — Nanopublication guidelines (https://nanopub.net/guidelines/working_draft/, undated on page): three named graphs linked by `np:hasAssertion`, `np:hasProvenance`, `np:hasPublicationInfo` from an `np:Nanopublication` head; PROV terms (`prov:wasDerivedFrom`, `prov:wasAttributedTo`) used in the provenance graph; identifiers are Trusty URIs carrying a content hash. The page itself does not discuss retraction.
- **OBSERVED** — `nanopub-java` `NPX` vocabulary (namespace `http://purl.org/nanopub/x/`, https://raw.githubusercontent.com/Nanopublication/nanopub-java/master/src/main/java/org/nanopub/vocabulary/NPX.java) defines `RETRACTS`, `SUPERSEDES`, `INVALIDATES`, `HAS_NANOPUB_TYPE`, `SIGNED_BY`, `HAS_SIGNATURE`, `INTRODUCES`, `DESCRIBES`, `APPROVES_OF`, index/trust terms.
- **OBSERVED** — Micropublications (Clark, Ciccarese, Goble, *J. Biomed. Semantics* 5:28, 2014; PMC4530550; arXiv:1305.3506; OWL at `http://purl.org/mp`): a Micropublication is "a set of Representations, having supports and/or challenges relations to one another"; Claim = "the single principal Statement arguedBy a Micropublication"; Evidence = Data / Method ("a reusable recipe showing how the Data were obtained") / Material / Reference; relations `supports` (transitive), `challenges`, `qualifies`. Distinguishing sentence vs nanopubs: "None of these models provide a means to transitively close claim lineages to underlying empirical evidence."
- **OBSERVED** — SEPIO repository (https://github.com/monarch-initiative/SEPIO-ontology) carries a prominent notice that the ontology "is out of date with the most recent developments" and development moved to a LinkML-based model. Not pursued further.
- **OBSERVED (ASSERTED by GRADE authors)** — GRADE handbook (https://gdt.gradepro.org/app/handbook/handbook.html): evidence profile vs summary-of-findings table; four certainty levels ("High: We are very confident that the true effect lies close to that of the estimate" … "Very Low: The true effect is likely to be substantially different from the estimate"); five down-rating domains (risk of bias, inconsistency, indirectness, imprecision, publication bias) and three up-rating factors; certainty is rated per outcome and "is likely to differ — from one outcome to another."
- **OBSERVED (ASSERTED by project)** — DISK (https://disk-project.org/): "a novel framework to test and revise hypotheses based on automatic analysis of scientific data repositories that grow over time"; "The provenance of the revised hypotheses is recorded, with all the details of the analyses." Ontology details not on the landing page.
- **DERIVED** — These are the only surveyed systems that model *claim support* rather than execution. Nanopub gives: claim ⊥ provenance ⊥ publication-info separation, content-hash identity, and explicit retract/supersede/invalidate. Micropublications give: claim → supports/challenges → data → method transitive closure — literally "claim lineage." GRADE gives the interpretation layer (named reasons to lower/raise confidence) but as a human rubric, not a machine schema. None models an "unavailable" evidence state per field; GRADE's imprecision/indirectness domains are the closest analogue at the interpretation layer.

Dataset identity/versioning only — no run or claim semantics.

### 2.8 Supply-chain attestation: in-toto, SLSA, Sigstore/Rekor, reproducible builds

- **OBSERVED** — in-toto Attestation Framework spec (repo HEAD `96c8d058c50384adca121ab7f914ba050e892ea3`, 2026-08-04; spec/README reports v1.2; Statement type `https://in-toto.io/Statement/v1`): layers Envelope (DSSE) → Statement (`_type`, `subject[]` = name + digest, `predicateType`, `predicate`) → Predicate ("arbitrary metadata about a subject artifact, with a type-specific schema") → Bundle. Predicate directory: `cyclonedx, link, provenance, reference, release, runtime-trace, scai, spdx, spdx2, spdx3, svr, test-result, vsa, vuln, vulns_02`.
- **OBSERVED** — Test Result predicate (`https://in-toto.io/attestation/test-result/v0.1`): "each attestation corresponds to one invocation of a test suite"; fields `result: PASSED|WARNED|FAILED`, `configuration: [ResourceDescriptor]`, `url`, `passedTests[]`, `warnedTests[]`, `failedTests[]`; verification policy may require only a subset ("it only matters that the tests passed on the corresponding test device of type A").
- **OBSERVED** — SCAI predicate v0.3 (`https://in-toto.io/attestation/scai/v0.3`): `attributes[] {attribute, target?, conditions?, evidence?}`, `producer?`; "does not dictate the types of attributes that can be attested, nor does it prescribe any format to the evidence"; parsing rules "Consumers MUST ignore unrecognized fields."
- **OBSERVED** — SLSA Provenance v1 (`https://slsa.dev/provenance/v1`, https://slsa.dev/spec/v1.0/provenance): `buildDefinition{buildType, externalParameters, internalParameters, resolvedDependencies}`, `runDetails{builder{id, builderDependencies, version}, metadata{invocationId, startedOn, finishedOn}, byproducts}`; `ResourceDescriptor{uri, digest, name, downloadLocation, mediaType, content, annotations}`; `externalParameters` "MUST be complete at SLSA Build L3"; `resolvedDependencies` "Completeness is best effort, at least through SLSA Build L3."
- **OBSERVED** — SLSA Provenance v0.2 (`https://slsa.dev/provenance/v0.2`) had explicit completeness claims: `metadata.completeness.parameters` ("If true, the builder claims that invocation.parameters is complete"), `.environment`, `.materials` ("… usually through some controls to prevent network access"), and `metadata.reproducible` ("… will produce bit-for-bit identical output").
- **OBSERVED (ASSERTED by Sigstore docs)** — Rekor (https://docs.sigstore.dev/logging/overview/): "an immutable, tamper-resistant ledger of metadata generated within a software project's supply chain"; auditors verify inclusion proofs and that "the log remains append-only and entries are never mutated or removed." Nothing about artifact correctness.
- **OBSERVED (thin)** — reproducible-builds.org "recording" page: Debian `.buildinfo` (control-file format, usually OpenPGP-signed; buildinfo.debian.net), Arch `.BUILDINFO` key=value in the package. The rebuilder comparison process is described elsewhere; not fetched.
- **DERIVED — answer to "is an in-toto predicate per transition a natural fit?"** Technically yes and semantically empty. A Statement binds a *set of subject digests* to a *typed predicate* and a *signer*; a transition `trials → cohort` can be expressed as Statement{subject = [cohort.json digest], predicate = {inputs: [trial digests], rule, exclusions…}} and chained. The framework gives you: content-addressed subject binding, typed predicate versioning (`predicateType` URI), signing (DSSE), bundling, transparency-log anchoring (Rekor), and a policy-engine mental model ("verify multiple attestations"). It gives you nothing about evaluation semantics; every field eval-evidence cares about would live in a predicate you define. SLSA v0.2's `completeness.*` booleans and SLSA v1's "best effort" wording are the nearest precedent for an honest "this list may be incomplete" marker — coarse (per-list booleans), not per-field state. Also note eval-evidence's `TRUST_MODEL.md` says `attestation.signature` is null in v0.1 and lists a 7-point gate before signing; DSSE + Rekor answer several of those points (signer identity, replay/timestamp via log) but not "which facts the signer directly observed."

### 2.9 Evaluation frameworks and their log formats

**Inspect AI** (UKGovernmentBEIS/inspect_ai, HEAD `7b17bdfed616e6284c7550f585e4552636f75ee7`, 2026-08-16; `src/inspect_ai/log/_log.py`, `_edit.py`) — all **OBSERVED** in source:
- `EvalLog{version=2, status ∈ {"started","success","cancelled","error"}, eval: EvalSpec, plan, results, stats, error, invalidated: bool ("Whether any samples were invalidated."), log_updates: list[LogUpdate], config_updates, tags, metadata, samples, reductions}`.
- `EvalSpec{eval_set_id, eval_id, run_id, created, task, task_id, task_version, task_file, task_registry_name, task_args, task_args_passed, solver, solver_args, dataset: EvalDataset{name, location, samples, sample_ids, shuffled}, sandbox, model, model_generate_config, model_base_url, model_args, model_roles, config: EvalConfig, revision: EvalRevision{type="git", origin, commit, dirty}, packages: dict[str,str], scorers, metrics}`.
- `EvalConfig{limit, sample_id, sample_shuffle, epochs, epochs_reducer, fail_on_error, continue_on_fail, retry_on_error, score_on_error, message_limit, token_limit, time_limit, working_limit, cost_limit, max_samples, …}`.
- `EvalSample{id, epoch, input, target, sandbox, messages, output, scores, metadata, store, events, model_usage, model_fallbacks, started_at, completed_at, uuid, invalidation: ProvenanceData | None ("Provenance data for invalidation."), error, error_retries: list[EvalRetryError] ("Errors that were retried for this sample."), limit: EvalSampleLimit, …}`.
- `ProvenanceData{timestamp, author: str, reason: str | None, metadata}` — "Metadata about who made an edit and why."; `LogUpdate{edits: [TagsEdit|MetadataEdit], provenance: ProvenanceData}` — "A group of edits that share provenance."
- `invalidate_samples(log, sample_uuids | "all", provenance)` — "Additionally, sets `EvalLog.invalidated = True`. Logs with invalidated samples will be automatically retried when executing eval sets."; `uninvalidate_samples(...)` exists.
- `EvalResults{total_samples ("Total samples in eval (dataset samples * epochs)"), completed_samples ("Samples completed without error. Will be equal to total_samples except when --fail-on-error is enabled or when there is early stopping."), early_stopping, scores: list[EvalScore]}`; `EvalScore{name, scorer, reducer, scored_samples, unscored_samples, params, metrics}`; `EvalSampleReductions{scorer, reducer, samples}`.
- **DERIVED** — Inspect's log already carries: expected denominator (`dataset.samples`, `sample_ids`, `epochs` → `total_samples`), completed denominator, per-scorer scored/unscored counts, per-sample retries, per-sample limits (why a sample stopped), harness identity (`revision{origin, commit, dirty}`, `packages`), and a *post-hoc exclusion record with author + reason + timestamp* plus a general edit log with provenance. This is the closest in-domain implementation of "selection/denominator history" and directly overlaps eval-evidence's Known-gap ("does not encode expected attempts, exclusions, retries, supersession, regrades, or aggregation"). It does **not** carry per-field evidence states, digests of inputs, or a cross-run/cross-model claim record; `EvalStatus` and `ProvenanceData.reason` are free text.

## 4. Explicit answers to the lane questions

**Which existing systems already solve part of "reconstruct a benchmark claim from evidence"?**
- Lineage relations: PROV-DM (complete vocabulary), RO-Crate/Workflow Run profiles (packaging), OpenLineage/W&B/MLflow (run↔artifact graphs). Evidence: §2.1, §2.3, §2.6.
- Selection/denominator history: Inspect AI (per-sample `invalidation` with author/reason, `log_updates`, retries, total/completed/scored/unscored) is the only in-domain implementation; Nextflow trace `attempt`/`error_action` at task level; lm-eval `n-samples{original,effective}`; HELM prospective caps. Evidence: §2.9, §2.6.
- Governance/verification of a leaderboard row: MLPerf (mandated instrument, checker, review, audit); ARC Prize tiers; Epoch's n-runs + SE. Evidence: §2.10.
- Claim support (assertion vs provenance vs interpretation): nanopublications, Micropublications, GRADE. Evidence: §2.5.
- Signed binding of typed statements to digest-identified subjects: in-toto (+ Rekor). Evidence: §2.8.
- Reported-score record with source/uncertainty/instance-file checksum: Every Eval Ever; interpretive layer: Evaluation Cards. Evidence: §2.9.

**Does any of them reconstruct a CLAIM rather than a run?** Only nanopub/Micropublications (as models) and MLPerf (as a procedure) operate at the claim/row level; EEE and Evaluation Cards operate at the *reported score* level but do not encode the lineage from trials. Every execution/experiment system stops at the run.

**Does any preserve which items were excluded and why?** Inspect (yes, per sample, with author/reason/timestamp; plus retries and unscored counts). MLPerf (procedurally, via withdrawal/objection records outside the data). Everything else: no, or "absent = not recorded" (Provenance Run Crate explicitly drops skipped steps).

**Does any represent UNAVAILABLE explicitly?** No surveyed system has a per-field evidence-state with an "unavailable" value. Nearest precedents: SLSA v0.2 `metadata.completeness.{parameters,environment,materials}` booleans (a producer says "this list is/isn't complete"); EEE `eval_library.version: "unknown"` convention and `has_unknown_level`; Evaluation Cards' "undisclosed fields appear alongside disclosed ones"; GRADE's graded certainty. PROV/RO-Crate/OpenLineage/MLflow: absence only.

**Does any distinguish evidence provenance from truth?** PROV (validity = consistency, explicit); in-toto (attestation = authenticated claim); nanopub (assertion/provenance split); Rekor (log ≠ correctness); MLPerf (replicability requirement, checker, audit); EEE/Evaluation Cards (first- vs third-party, documentation vs run). Trackers/lineage tools do not.

**Could eval-evidence reuse it directly?** PROV-O/JSON-LD terms for the lineage record; RO-Crate as the container; in-toto Statement/DSSE for signing; Inspect's `ProvenanceData` shape for exclusions/edits; EEE's `source_type`/`evaluator_relationship`/`uncertainty`/`detailed_evaluation_results{checksum,total_rows}` for the reported-number record; OTel `gen_ai.*` (incl. `gen_ai.evaluation.result`) as transport; lm-eval-style content hashes for task identity.

**Does any make part/all of eval-evidence unnecessary?** Parts: (a) a bespoke bundle envelope (RO-Crate/in-toto already do file+digest+role+conformsTo); (b) a bespoke signing design (DSSE/in-toto/Rekor); (c) a bespoke exclusion-record design (Inspect's pattern); (d) a bespoke lineage vocabulary (PROV). Not replaced by anything: the per-field evidence-state vocabulary with source pointers, and a claim-specific "required evidence → state → unresolved differences → decision" record. Whether trial-level byte sealing is redundant depends on Harbor's own locks/manifests (other lanes; Harbor has `TrialLock`, `JobLock`, `artifact_manifest` at the pinned revision — OBSERVED file presence only).

## 6. Synthesis

### (a) Which existing abstraction is closest to "claim lineage"?

Restating the target: retained trials → eligible → included cohort → transformations → aggregation → reported number → table location → claim.

- **PROV-DM with a profile** is the closest *data-model* fit and needs no invention for the relations: each retained trial result is a `prov:Entity` (with `prov:value`/digest), "eligible" and "included" are `prov:Collection`s with `hadMember`, membership decisions are `prov:Activity`s with a `prov:Plan` (the rule) and an `prov:Agent` (who), transformations/aggregation are Activities with `used`/`wasGeneratedBy`, the reported number `wasDerivedFrom` the included collection, the table cell is an Entity `specializationOf` the number, the claim `wasDerivedFrom` the cell, supersession is `wasRevisionOf`, removal is `wasInvalidatedBy`, and the whole record is a `prov:Bundle` (so the lineage itself has provenance). PROV-CONSTRAINTS gives you consistency checking and the explicit stance that validity ≠ truth. What PROV lacks: an evidence-state per attribute (observed/derived/asserted/unavailable) and any eval-domain schema (what fields matter). Verdict: **it is "PROV-DM with a profile" for the graph; the profile is where all the work is.**
- **Workflow Run RO-Crate** is the same idea serialised in schema.org and packaged with the files; it would be a fine *container* (conformsTo + hasPart + digests) but its published profiles are worse than PROV for this purpose because they drop skipped steps and default to success.
- **An in-toto attestation chain** is the closest fit for *binding and signing* transitions (subject digests + typed predicate + signer), and Rekor for anchoring; it is not a lineage model — the predicate is the lineage model. If signing is out of scope for now (it is: `attestation.signature` is null in v0.1), in-toto adds ceremony without content.
- **MLPerf's submission rules** are the closest fit for the *governance* question ("is this row supported?") but are a convention + checker + committee, tuned to one deterministic-ish benchmark family with one valid run per scenario; they do not travel.
- **Inspect's log** is the closest fit for the *retained trials → eligible → included* segment in the AI-eval domain specifically (invalidation with reason, retries, scored/unscored, epochs reducer) — but only within one eval log; it has no cross-run or cross-model claim record.

Net: the lineage segment is PROV-shaped; the exclusion segment is Inspect-shaped; the reported-number segment is EEE-shaped; the claim-support segment is nanopub/Micropublication-shaped; the row-governance segment is MLPerf-shaped. No single system spans all five, and no system anywhere has per-field "unavailable."

### (b) Established equivalents for the eval-evidence evidence-state vocabulary

| eval-evidence status | Nearest established equivalent(s) | Fit |
|---|---|---|
| `observed` | PROV `hadPrimarySource` (weak); SLSA "builder observed" semantics; EEE `source_type=evaluation_run`; MLPerf "logs produced by LoadGen"; Evaluation Cards first-party-vs-third-party is orthogonal | Partial — no standard says "this value was read directly from a retained primary artifact at pointer X" |
| `derived` | PROV `wasDerivedFrom` + Activity/Plan; DVC stage (cmd + dep hashes → out); lm-eval hashes | Good — PROV qualified derivation with a named transform is exactly this |
| `operator_asserted` | PROV `wasAttributedTo` a human/organisation Agent; nanopub provenance graph attribution; EEE `evaluator_relationship=third_party/first_party` (record-level); in-toto "attester" | Partial — attribution exists; the "asserted, not observed" flavour must be conveyed by agent role |
| `provider_asserted` | Same as above with Agent = model provider; OTel `gen_ai.response.model` "as reported by the provider"; EEE `source_type=documentation` | Partial |
| `unavailable` | **None per field.** Precedents: SLSA v0.2 `metadata.completeness.*` (list-level booleans); EEE `"unknown"` string; Evaluation Cards "undisclosed shown alongside disclosed"; GRADE certainty (interpretation-level) | Gap — this is genuinely novel as a per-field, source-pointed state |

Also `conflicting` (used in eval-evidence's `extensions.harbor.source_conflicts`): PROV `alternateOf` can state that two entities are views of the same thing but cannot state that their values disagree; nanopub `challenges`/Micropublication `challenges` express disagreement between *claims*; no execution-record schema surveyed represents "two retained sources for one field disagree, unresolved."

### (c) Does anything mature represent "claim support" (evidence + controls + assumptions + unresolved alternatives ⇒ interpretation)?

- **Nanopublications**: yes for the *separation* (assertion / provenance / publication info) and *lifecycle* (`npx:supersedes`, `retracts`, `invalidates`; content-hash IDs; signatures). No notion of controls/assumptions.
- **Micropublications**: yes for the *argument graph* (claim ← supports/challenges ← data ← method), explicitly designed to "transitively close claim lineages to underlying empirical evidence." Assumptions/qualifiers exist as `qualifies`.
- **GRADE**: yes for the *interpretation rubric* — named reasons (risk of bias, inconsistency, indirectness, imprecision, publication bias) that lower certainty in an estimate; per-outcome. It is the closest thing to eval-evidence's "unresolved differences ⇒ decision" but is human judgment, not a schema.
- **SCAI (in-toto)**: `attribute + conditions + evidence` per assertion — a compact machine form of "claim + assumptions + evidence" for artifacts.
- **Toulmin/ASPIC/argumentation frameworks**: NOT FETCHED here; conceptually they are what Micropublications formalise (claim/warrant/backing/rebuttal). No mature eval tooling implements them.
- **DISK**: records how a hypothesis was tested and revised with provenance (ASSERTED by project page).
- **MLPerf**: the "controls" are the compliance tests (`TEST01/04/06`) and seed/duration checks; the "unresolved alternatives" are objections; the "interpretation" is Available/Preview/RDI + Closed/Open placement. It is a full claim-support *process*, encoded in rules and a checker rather than in a portable record.

### (d) Frank recommendation

1. **Do not invent a lineage vocabulary.** Express the campaign/claim lineage as a PROV profile (JSON-LD with `prov:` terms, or PROV-N), optionally packaged as an RO-Crate; this gives Collections/membership, derivation, revision, invalidation, bundles, and a well-understood validity notion for free. If serialising as JSON-LD, the eval-evidence "structured-provenance companion record" (`status`, `source_ref{input_path, json_pointer, input_sha256}`, `transform{name, version}`, `candidates`) becomes an annotation on a qualified derivation, not a competing format.
2. **Do not invent an exclusion record.** Copy Inspect's shape: `{timestamp, author, reason, metadata}` attached to the excluded unit, plus a log of post-hoc edits with the same provenance; report `total/completed/scored/unscored` (or Harbor's expected/discovered/included) as counts next to the aggregate. Then E1 becomes "does Harbor's job state let us fill Inspect-equivalent fields," which is a sharper experiment.
3. **Do not invent signing.** If/when `attestation.signature` becomes non-null, wrap the record as an in-toto Statement (subject = digest of the lineage/claim record; predicateType = a versioned eval-evidence URI) in DSSE, and optionally log to Rekor. This discharges TRUST_MODEL gate items 1–4 with existing tooling; item 5 ("which facts the signer directly observed") is exactly the per-field evidence state, which no existing predicate provides — that is the one thing worth writing as a predicate.
4. **Do not invent a reported-score record.** Every Eval Ever already has `source_type`, `evaluator_relationship`, `uncertainty{se, ci, method, num_samples}`, `detailed_evaluation_results{checksum, total_rows}`, `sample_hash`; align field names or emit EEE from the lineage record so Evaluation Cards can consume it.
5. **Keep and sharpen the only novel part**: the per-field evidence-state vocabulary with source pointers, its "unavailable is not null" boundary, and the claim-specific decision record (`claim → required evidence → state → unresolved differences → decision`). Precedents to cite for legitimacy rather than novelty: SLSA v0.2 completeness flags, EEE "unknown," Evaluation Cards' undisclosed-alongside-disclosed, GRADE's named down-rating domains.
6. **Treat MLPerf as the design template for the checker, not the format**: a row is valid iff a re-derivation from mandated logs passes; anything the checker cannot re-derive is an error, and human objection/audit handles the rest. The eval-evidence equivalent is a `verify` that recomputes the aggregate from the included collection and refuses when membership or transform is not reconstructable — which the DECISION_GATE already gestures at.
7. **The trial-level byte-sealing bundle is the most redundant component** relative to prior art (RO-Crate/in-toto/Harbor manifests all do file+digest), and, per "Leaderboard Illusion" and the HF details/contents observation, sealing trials does nothing for the failure mode that actually mattered (selection/retraction). If E4 finds Harbor's locks/manifests cover the surface, drop it and keep only normalisation/comparison.

---

## 7. Implications for the central question

"What evidence is required for an independent person to reconstruct an evaluation claim?" — Prior art answers this piecemeal and, read together, says: the *relations* are solved (PROV), the *run record* is solved many times over (Inspect, HELM, lm-eval, MLflow/W&B, CWLProv, RO-Crate), *governance* is solved within a closed program (MLPerf), and *claim publication with lifecycle* is solved for scientific statements (nanopub/Micropublications). What is not solved anywhere is the middle: a portable record that (i) names the expected denominator and every exclusion with a reason, (ii) states per field whether a value was observed at a pointer, derived by a named transform, asserted by whom, or unavailable, and (iii) recomputes the reported number from the included set or refuses. The proposed eval-evidence abstraction is unnecessary as a *bundle format* and as a *lineage vocabulary* — those should be borrowed. It is not unnecessary as (ii) + (iii): no surveyed system represents unavailability or unresolved conflict per field, and only Inspect represents exclusion-with-reason at all. The most decision-relevant single observation is that the strongest in-domain log format (Inspect) already implements the denominator/exclusion half natively — which both shrinks the eval-evidence surface and gives E1/E6 a concrete target to measure Harbor against.
