## 1. Verdict (one paragraph)

Harbor's native state already preserves *most* of what an independent reviewer needs to recompute a **job-level** number, and it preserves it in typed, content-addressed form: per-trial `result.json` (task identity incl. git commit or package ref, `task_checksum`, configured agent/model, verifier rewards, exception type, timings), per-trial `config.json`, per-trial and per-job `lock.json` (task content digest, task version, harbor version/commit-when-known, resolved agent/env/verifier config, retry policy, regrade lineage), and a job `result.json` whose `stats.evals[*].metrics[{"mean"}]` is exactly recomputable from the trial `result.json` files (I recomputed the Harbor `mean` and the tbench.ai TB 2.0 accuracy for one real public row, 280/445 = 62.9%, from per-trial artifacts alone). What Harbor does **not** preserve natively is (a) the failed attempts behind a retry (the previous attempt directory is `shutil.rmtree`'d; only `n_retries` survives locally — the hub keeps them only if streaming upload happened), (b) any attempt/run index (five attempts of a task are indistinguishable configs with random trial names, so "std over 5 runs" is not recoverable), (c) never-started trials (present only as `n_total_trials − n_completed_trials`), (d) the aggregation *policy* (that `mean` counts errored/None-reward trials as 0 is a code fact, not a recorded one), (e) which of several same-task, same-config trials or regrades is "authoritative", (f) harness version for jobs made before 2026-04-29 (job lock) / 2026-06-29 (trial lock), and (g) publication state — which is owned entirely by a separate layer (the TB 2.1 `leaderboard/submissions/*.json` records + Harbor Hub rows) that *does* record source jobs, filter, included trial UUIDs, disqualifications and computed metrics, but references trials by hub UUID on a hosted service whose visibility has already gone dark once (issue #177). Net: a Terminal-Bench leaderboard **accuracy** is reconstructable from Harbor native state (given the trial dirs and the published aggregation rule); the **uncertainty** and the **membership/exclusion decisions** are reconstructable only from the leaderboard layer's record, and only while the hub serves the referenced trials.

### Q: Could a reviewer holding only the job directory reconstruct a reported job-level number?

- **Harbor `mean` (job `result.json`)**: YES, exactly, from the trial `result.json` files, *provided* the reviewer knows the rule (None→0, denominator = every trial dir with a `result.json`, grouping by `agent__model__source`). Verified on the 17 oracle jobs (trivially) and on the two public TB2 job dirs (61/89, 219/356). The rule itself is not in the artifact.
- **tbench.ai TB2.0 accuracy**: YES for the row I tested (280/445 = 62.9%) — but only after learning from the TB2.1 repo that errored trials count 0 and that the submission's *set of jobs* is the union in the HF directory. The 2.0 HF README does not state the aggregation.
- **tbench.ai TB2.0 ±**: NO — method undocumented, run partition not encoded.
- **TB2.1 accuracy ± SE, pass@k, hacks**: YES from `submissions/<name>.json` + hub trial rows + `core/metrics.py` (formula published), **while** the hub serves the referenced trials; from a job directory alone you cannot know which trials were disqualified or whether "latest attempt" on the hub equals what is on disk.

### Q: What exactly is missing (smallest things)?

1. An attempt/run index (or ordinal) on `TrialConfig`/`TrialResult` — without it "run k of 5" and any run-level dispersion are irrecoverable.
2. A per-trial retry record (prior attempt ids/exception types) instead of only `n_retries` and an `rmtree`.
3. The aggregation policy stamped into `stats` (e.g. `errored_as_zero: true`, `denominator: n_result_files`, metric implementation version).
4. A label for which task hash algorithm produced `task_checksum` vs `lock.task.digest` (or drop the deprecated one).
5. A backward "regraded_by/superseded_by" marker or a job-level authoritative-set declaration.
6. For publication: the leaderboard record already has membership+exclusions+metrics; missing is an offline-durable copy of the referenced trial `result.json`s (or their digests) so the row is auditable without the hub.

## 5. Implications for the central question

1. **Trial-level verification is already the well-served part.** Harbor's `result.json` + `lock.json` (v0.17.0+) + hub archive allowlist give a reviewer typed task identity, content digests, task version, resolved config, timings, verifier outputs and (for LiteLLM agents) response model ids per step. A separate trial-scoped envelope that re-hashes these files adds custody, not information; the eval-evidence `HARBOR_MAPPING.md` gaps (`harness_version/commit`, `verifier_digest`, `task_revision`) are mostly closed by reading `lock.json`, which the adapter currently ignores.
2. **The reconstruction gap is between "trials" and "the number", and it is small and concrete, not abstract.** Everything missing is enumerable: attempt ordinal, per-trial retry record, aggregation-policy stamp, hash-algorithm label, regrade authority marker. These are Harbor-model fields, not a new evidence ontology. The TB2.1 `submissions/<name>.json` already *is* the "campaign record" the eval-evidence docs sketch (source jobs, filter, included trial ids, exclusions with reasons, computed metrics with a published formula, PR provenance) — it lives, correctly, in the leaderboard layer.
3. **The remaining fragility is hosting, not schema.** The TB2.1 record references trials by hub UUID; when hub visibility lapsed (#177) rows reported `n_trials: 0` and the record became unauditable, though the JSON in git was unchanged. An offline-durable per-row bundle (trial `result.json` digests + `lock.json` digests, or the cloned archives themselves) is the smallest thing that would let a third party audit a row without the service. That is the one place a portable, self-contained artifact adds value — and it is a per-*row* (publication) artifact, not a per-trial one.
4. **Aggregation policy is a code fact, and it drifts across layers.** Harbor `mean` (value, None→0), TB2.0 (unknown ±), TB2.1 (`reward>0`, per-task SE, disqualified→0, tokens still counted), Hub rows (declared). A reviewer needs the *rule and its version* recorded next to the number; today it must be recovered from source at the right commit.
5. **Evidence is destroyed by design in two places** — retried attempts (`rmtree`) and resume cleanup — and mutated after write in one (`_scrub_jobs_dir`). Any digest-based scheme must be applied after the last Harbor-side mutation and must accept that the retry history exists only if uploads were streamed.
6. On the framing: "the proposed abstraction" (a generic evidence envelope) is **unnecessary for the trial layer** and **premature for the aggregation layer** in the Terminal-Bench ecosystem, because the native systems have converged (2026-06..08) on locks, hub clones, and a leaderboard record with published metric code. What is not yet native and would be cheap: (i) the five Harbor fields above, (ii) an offline copy/digest set attached to each leaderboard row, (iii) a stamped aggregation policy. Everything else in this lane is either present or a hosting-availability problem.
